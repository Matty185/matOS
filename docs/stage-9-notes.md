# Stage 9 Session Notes

**Date:** 2026-07-19
**Scope:** Seed script (`scripts/seed.ts`), per `matos_project_plan.md` §10 row 9 — "Northside BJJ, 1
owner + 1 coach, 18 members varied belts/plans/join dates, 3 months realistic attendance, mixed payment
statuses, 3–4 promotions, 2 mock analyses, athlete logs on 3–4 members." No review-gate agents are
listed against this row in the plan's Build Sequence table (unlike Stages 1, 4–8, 11).

---

## What was done

- **`scripts/seed.ts`** — service-role, re-runnable wipe+reseed. Run with `npx tsx scripts/seed.ts`
  (also aliased as `npm run seed`). Produces:
  - Northside BJJ gym (found-or-created, never deleted — see below), 1 owner, 1 coach, 16 athletes.
  - Belts spanning the full range CLAUDE.md calls for: adult white through black, plus three kids-family
    belts (grey_white, yellow, orange_black) in the same member list.
  - Plans mixed (monthly/casual/comp_team), join dates from 14 days to ~3.3 years ago.
  - A 10-class weekly schedule (Mon–Sat; gi/no-gi/open mat/comp, plus two kids classes) and ~330
    attendance rows generated by walking the last 13 weeks day-by-day and rolling a per-member
    attendance probability against their personal regular-class list.
  - 6 trailing months of payments per member (paid/unpaid/waived mixed), including 3 genuinely overdue
    members (unpaid + period already ended) and the current month left unpaid gym-wide (not yet overdue).
  - 4 belt promotions (`belt_history`: a starting-belt row + a promotion row each), 2 mock analyses and
    4 members with athlete-log entries — both requested ranges ("3–4 promotions" / "3–4 members") hit
    at their upper bound.
  - `gdpr_consents` for all 18 members, matching what the real invite-claim flow would have captured.
- **Three real logins**, per the user's explicit choice on how to handle credentials this stage:
  - Owner (`matijukm@gmail.com`) — the existing auth account is _found_, never recreated or
    password-reset, and simply relinked to a fresh `members` row each run. The user's own login never
    changes across re-seeds.
  - Coach (`coach@northsidebjj.demo`) and one demo athlete (`demo.athlete@northsidebjj.demo`,
    seeded as "Aoife Byrne") — created on first run, password-reset on every later run, so the script
    stays re-runnable without needing to remember a prior password. Both passwords are printed at the
    end of every run.
- **CSP fix in `next.config.mjs`** — found via this stage's live verification, not something the seed
  script itself caused: the coach Attendance page's Supabase Realtime subscription (a Stage 5 /
  CLAUDE.md-mandated feature — "Attendance view uses Supabase realtime") was being silently blocked by
  the browser, because `connect-src` listed `*.supabase.co` but not the `wss:` scheme the realtime
  websocket connects over. Added `wss://*.supabase.co` explicitly. Fixed immediately per the standing
  "fix findings immediately" rule rather than filed away, even though it wasn't a Stage 9 deliverable.

## Decisions beyond the plan's literal text

1. **Wipe scope is deliberately narrower than "wipe everything."** Two things are never touched:
   - The `gyms` row itself is found-or-created, never deleted — real `audit_log` rows from Stages 6–8's
     live testing already reference it (`gym_id on delete restrict`), so a hard delete would fail
     outright, and there's no need to fight that: reusing the same gym id keeps it stable across re-runs.
   - `audit_log` rows are never touched. The table's own trigger blocks UPDATE/DELETE unconditionally,
     even for the service-role client (`audit_log_no_delete`/`audit_log_no_update` in the Stage 1 RLS
     migration) — "immutable" per CLAUDE.md Rule 6 applies to the seed script too, not just app code.
     Seeding also never _writes_ audit_log rows: seeded rows are fixture data representing an
     already-established gym's history, not real user actions, so there's nothing genuine to log.
   - Every other gym-scoped table (`members`, `attendance`, `payments`, `belt_history`, `analyses`,
     `athlete_logs`, `gdpr_consents`, `classes`, `invites`, `deletion_requests`, `notifications`,
     `agent_rate_limits`) is deleted and rebuilt from scratch on every run, in FK-safe dependency order.
   - Other gyms in the same Supabase project (leftover throwaway "Stage N Verify Gym" rows from every
     prior stage's live-verification scripts) are left alone — never in scope for this script, which
     only ever touches rows where `gym_id` matches Northside BJJ.
2. **Two mock analyses both go to the one demo-login athlete, not two different members.** The plan just
   says "2 mock analyses" without specifying whose. `analyses.created_by` references `auth.users`, and
   only one athlete has a real auth account — giving both to her keeps `created_by` meaningfully tied to
   a real self-service upload (matching how the feature actually works) instead of leaving it null for a
   member with no login.
3. **Payment generation window matches the payments grid's own 6-month rolling window exactly, not the
   plan's unspecified length.** First attempt used 5 months and looked broken on live verification: the
   grid (`WINDOW_LENGTH = 6` in `src/app/(coach)/payments/page.tsx`) showed its oldest column as
   "Overdue" for nearly every member, because `overdue.ts` treats a missing payment row as unpaid by
   default. Extended to 6 months so every visible grid cell has a real row.
4. **Timestamps are constructed with an explicitly-computed Ireland UTC offset (EU DST rule, last Sunday
   March–October), never via a local `Date` + `toISOString()`.** This project has hit the "local
   midnight rollback near a UTC+1 host" bug three separate times (Stages 6, 7, 8 test fixtures) — the
   seed script sidesteps the whole bug class by doing all date arithmetic in plain UTC and only
   attaching a real, date-correct `+01:00`/`+00:00` offset at the point a timestamp is built, so it stays
   correct however far in the future this script gets re-run.

## Verification

- Ran the script twice back-to-back to confirm re-runnability: second run produced the same shape (18
  members, 10 classes, ~330 attendance rows, correct payment/status mix) with fresh coach/athlete
  passwords and the owner's `auth.users` row/`updated_at` unchanged.
- DB-level checks: role/belt/plan distribution, no duplicate emails, 22 belt_history rows (18 starting +
  4 promotions), 18 gdpr_consents rows, exactly 2 analyses (`complete`, matching the app's real
  `buildMockReport()` JSON shape), 3 genuinely overdue payments (unpaid + period end < today).
- Live Playwright run against `localhost:3000` (dev server) logged in as the seeded coach and the seeded
  demo athlete (not the real owner account — its password is the user's own and was deliberately never
  reset, so it isn't known to any script) and checked Dashboard, Members, Payments, Attendance, Classes,
  Home, My Progress, and Upload. Confirmed correct overdue count (3), correct belt/plan rendering, a real
  8-week attendance streak, upcoming classes, belt-history/log entries, and both mock analyses rendering
  with real report content. Zero console errors after the CSP fix (one CSP violation before it).

## Known gaps / deferred
