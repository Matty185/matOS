# CLAUDE.md — MatOS

Persistent context for Claude Code and all ECC agents working on this repository. Read fully before any task. The companion document `matos_project_plan.md` contains the complete specification — this file is the operational summary. Where they conflict, the project plan wins.

## What This Is

MatOS is a multi-tenant BJJ gym management platform. Current phase: **alpha** — a functional demo with seeded fictional data (demo gym "Northside BJJ"), built for a technical collaborator demo and a first unpaid gym tester. Core differentiator: a natural-language agentic interface for coaches, plus a stubbed AI video analysis feature (real pipeline is a later phase — **no video is ever stored, process-and-discard model**).

**2026-07-26 — now also expanding into a Solo Athlete Platform + native mobile app.** Companion spec: `matos_mobile_plan.md` (repo root) — where they conflict with anything below, the mobile plan wins for the account-primary/mobile scope; this file and `matos_project_plan.md` remain authoritative for the existing web alpha otherwise. See that plan's own §2.1 for the account-primary schema/RLS direction (Stage S1, BLOCKING-gated) that will eventually make "every user has exactly one gym" stop being a safe assumption anywhere in this codebase.

## Architecture Rules

1. **Multi-tenant from day one.** Every tenant table has `gym_id` (FK, indexed). One gym exists in alpha; the model supports many.
2. **RLS at the database layer is the security boundary.** Application-layer checks are UX convenience only. Every table has RLS enabled. No public SELECT on anything.
3. **Roles:** `gym_owner` > `coach` > `athlete`. Owner adds gym settings + coach management on top of coach. Athletes see and touch ONLY their own data — enforced by RLS, and payment `amount` is additionally filtered server-side for athlete queries (two layers).
4. **Two Supabase clients:** browser client (RLS-respecting) for everything user-facing; service-role client (env var, server-only, never in bundle) ONLY for invite generation, audit log inserts, and seeding. The agent uses the RLS client exclusively.
5. **Every API route** is wrapped in `withAuth(handler, requiredRole?)`: session → gym_id match → role → Zod input validation → rate limit (agent route only). Error shape: `{ error, code, status }`. Never leak internals in errors.
6. **Deletes are mostly disabled.** Members are deactivated, not deleted. Audit log is immutable. GDPR deletion anonymises (see plan §7) rather than hard-deleting payments and audit entries.
7. **Classes use a template model** (recurring class + attendance dated by check-in timestamp). This is a known simplification — flag anything that would make the future refactor to per-session instances harder.
8. **Overdue is computed at query time**, never stored: `status = unpaid AND period end < today`. No grace period. `waived` is a manual coach override.

## Agentic Interface Rules (critical)

- `gym_id` is injected **server-side** into every tool call. Never trust it from model output.
- Tool parameters are validated server-side regardless of what the model returns.
- Read tools execute immediately. **All write tools require coach confirmation** in the UI before execution; confirmed writes go through the RESTful resource endpoints (not back through /api/agent).
- `deactivate_member` requires **typed** confirmation ("yes"/"confirm"), not a button.
- Tool results go back to the model as structured JSON, never interpolated into the prompt as prose. Member-entered text is untrusted — the system prompt says so explicitly. Model output is schema-validated before render and never rendered as raw HTML.
- Rate limit: soft warning at 40 queries/day, hard block at 50.
- Every agent action writes an audit_log row including the raw natural-language query.
- Tone: terse and functional. "Done. John Murphy marked as paid for June."
- Multi-step chaining is allowed (one batched confirmation). Disambiguate duplicate names by listing options with distinguishing detail. Out-of-scope queries get a brief redirect listing actual capabilities — no apologising.

## UI Standards

- Mobile-first: every screen works at 390px, touch targets ≥44px, no horizontal scroll, WCAG AA contrast.
- Proper empty states (with an action) on every list view. Loading states on every async action. Toasts for transient errors, inline for validation, fallback error page for the unhandled.
- Belt rendering always via the shared `<BeltDisplay />` component (belt colour + up to 4 stripe dots). Belt enum includes kids belts (grey/yellow/orange/green families) in the same member list.
- Belt promotion triggers a simple celebration animation.
- The agent lives in a floating button (React portal, fixed position) opening a chat panel. In-session history only.
- Attendance view uses Supabase realtime — check-ins appear live.

### What This Module Is

Layer 1: manual match breakdown — client-side video player + tagging tool producing a timestamped record (positional intervals with roles + discrete events with modifiers/outcomes). Layer 2: computed athlete profiles from accumulated breakdowns, with side-by-side comparison. AI tagging is **phase 2, not now** — do not build it, but do not block it (the `source` field on events exists from day one).

### Non-Negotiables

1. **Video never touches the server.** Playback is a local file via `URL.createObjectURL`. No upload endpoint, no storage, no video URLs in the database. Only `video_filename` + `video_duration_seconds` are stored (resume mismatch check).
2. **Single focus athlete per breakdown.** Everything is tagged from their perspective — the opponent's takedown attempt is the focus athlete's `takedown_defended`. Never design UI or data for two-athlete tagging.
3. **Taxonomy is data, not code.** Events, modifiers, and outcome rules live in the `event_types` seed table. Coach edits to the taxonomy must never require schema or component changes.
4. **Outcomes are conditionally required** per event_types (`outcome_required`). Validate server-side against `outcome_options`; the confirm sheet blocks only on required fields.
5. **Breakdowns are standalone artifacts** identified by name + user-entered `match_date` (required — it drives all trajectory ordering, since analysis can happen long after the match). Not replayable against video.
6. **Profiles are computed, not authored.** Gi/no-gi always separate. Every metric renders its n. Shown from n=1. Trajectory ordered by match_date, never created_at.
7. **External people** are gym-scoped analyst records (free-named, unlinked to accounts). No merging into member profiles — don't build for it.
8. **Ownership:** author owns a breakdown; one author, no collaboration. Coach/owner see all in gym. Breakdown deletion cascades its positions/events (allowed — unlike member records).
9. **Agent tools are read-only and factual.** Profile/metric/comparison queries return numbers. Never coaching advice — "what should X work on" gets the weakest metrics reported factually, nothing more. Same server-side gym_id injection and parameter validation as all existing tools.
10. **GDPR:** member deletion also deletes their member-linked breakdowns. The AI-transit compliance question (third-party opponents in footage) is deliberately deferred to phase 2 — do not introduce any server-side video processing in v1.

### Tagging UX Contract

Tap event → auto-pause → modifier/outcome sheet → confirm → resume. Two taps total for no-modifier events. Position tags open an interval; the next position tag closes the previous one. Timeline strip with tappable markers for edit/delete/timestamp adjust. Continuous local draft + explicit server save; resume warns on filename/duration mismatch but allows proceeding. Speeds 0.25×–2×. All alpha UI standards apply (390px, 44px targets, empty/loading/error states).

### Build Gates

Stage A1 (schema + RLS + event_types seed) is BLOCKING on security-reviewer + database-reviewer, same as alpha Stage 1. All-reviewer gates after tagging screen (A3), profiles (A5), and integration (A7). Full pass at A9. Never proceed past a security or critic BLOCKED item.

### Out of Scope — Match Analysis Module

AI tagging, video storage/upload/URLs, keyboard shortcuts, two-athlete tagging, canonical match linking, ruleset/points events, collaborative breakdowns, external-person merging, breakdown replay against video. Flag, don't build.

## Decision Log

### 2026-07-15 — Node version pin: 20 → 24

**Context.** CLAUDE.md and `package.json` (`engines`) pinned Node 20 LTS. Node 20 reached EOL 2026-04-30 (no further security patches). The local dev machine has been running Node 24.18.0 the entire time regardless of the pin, causing `EBADENGINE` warnings on every `npm install`. Node 22 (Active LTS, → Maintenance ~Oct 2026, EOL Apr 2027) and Node 24 (Active LTS, EOL Apr 2028, now Vercel's default for new projects) were the live options.

**Decision.** Pinned to Node 24 (`engines: ">=24 <25"`, `@types/node: ^24`).

**Reasoning.** The dev environment and almost certainly CI/Vercel builds have already been running on Node 24 in practice, so this pin change codifies the status quo rather than introducing a new untested runtime — Node 22 would mean adopting a _third_, still-unexercised version. Node 24 also has the longest runway (Apr 2028) of the two live options and is Vercel's new default, minimizing future churn for a solo-maintained alpha. Flagging per CLAUDE.md's "do not deviate without flagging" clause: this was resolved autonomously while the human was AFK; no code changes beyond the version pin were made, and a build/smoke test against Node 24 is still recommended before the next deploy.

**Alternatives considered.**

- _Node 22 (conservative Active LTS):_ rejected — less runway than 24, and would still be a version never actually run locally, so it doesn't remove the drift between documented and actual runtime.
- _Install Node 20 via nvm to match the existing pin:_ rejected — reinstalling an EOL, unpatched runtime for a network-facing demo app (Supabase Auth, Claude API, invite emails) to preserve a stale pin has real downside and no upside; "flag deviations" is satisfied by this log entry, not by manually enforcing a dead version.

### 2026-07-20 — CSP `unsafe-inline`/`unsafe-eval`, and Next 14.2.35's open npm audit advisories: accepted for alpha

**Context.** Stage 11's full pre-demo security review flagged two related gaps, both FLAGGED (not BLOCKED) by the reviewing agent: (1) `script-src` in `next.config.mjs` includes both `'unsafe-inline'` and `'unsafe-eval'`, which — together — mean CSP provides no real XSS mitigation if an injection sink is ever introduced (none exists today; no `dangerouslySetInnerHTML`/`innerHTML` anywhere in `src/`, confirmed by the review); (2) `npm audit --audit-level=high` reports 9 high-severity advisories against the installed `next@14.2.35` (Server Component DoS, request smuggling, redirect cache poisoning, SSRF, RSC cache poisoning, `beforeInteractive` script XSS), all requiring a Next 15/16 upgrade to resolve.

**Decision.** Dropped `'unsafe-eval'` from `script-src` in production only (kept in `next dev` — webpack's HMR eval-devtool needs it; a production client bundle doesn't). `'unsafe-inline'` stays for both — removing it needs a nonce threaded through Next's own framework-injected RSC hydration `<script>` tags, a real code change (middleware nonce generation + response-header wiring), not a config toggle. Left the Next.js version pin at 14.2.35, npm audit advisories un-remediated.

**Reasoning.** `'unsafe-eval'` in production was pure unnecessary exposure with a free, verified-safe removal (tested against a real `next build` + `next start` session, zero console/functionality regressions) — no reason to defer that part. The other two (the `'unsafe-inline'` nonce rework, and the Next 15/16 upgrade) are both real, non-trivial changes with meaningful blast radius — a mis-wired CSP nonce breaks hydration on every page, and a major-version framework upgrade this close to a demo risks the exact kind of last-minute breakage CLAUDE.md's own stack-pinning philosophy exists to avoid. Neither advisory is confirmed exploitable against this specific app's actual configuration (single-tenant-focused alpha, no public-facing attacker-supplied-URL rewrite/proxy usage that several of the advisories specifically target), and React's auto-escaping already closes the sink CSP's `script-src` would otherwise be the last line of defense against. Flagging per CLAUDE.md's "do not deviate without flagging" clause rather than carrying this forward silently a third time (it was already deferred once at Stage 0, and again — undetected — through Stage 10's polish pass).

**Alternatives considered.**

- _Implement a nonce-based CSP now, dropping `'unsafe-inline'` entirely:_ rejected for this pass — correct implementation requires per-request nonce generation in middleware plus confirming Next 14.2.35's exact framework-script nonce-detection behavior, which isn't something to get subtly wrong three days before a demo without the ability to verify against live Next.js framework documentation. Worth doing properly in a dedicated pass, not squeezed into this review's remaining scope.
- _Upgrade to Next 15 now to clear the audit advisories:_ rejected — breaking change, no patched 14.x point release exists, and forcing it this late trades a disclosed-but-unconfirmed risk for a real, immediate one (an upgrade regression during final demo prep).
- _Silently leave both as they were:_ rejected — CLAUDE.md's own "flag deviations" rule and the fact that this is literally the "pre-demo security pass" the Stage 0 deferral was written to be resolved at.

### 2026-07-26 — Stage S0: monorepo restructure, package-boundary decisions

**Context.** `matos_mobile_plan.md` §2.1 specifies the target shape (`apps/web`, `apps/mobile`, `packages/shared`) but leaves several boundary calls to the implementer: exactly what "Supabase client factory" in `packages/shared` means given web's existing client/server/service-role split is inherently Next.js-specific (cookies via `@supabase/ssr`, `next/headers`), how lint-staged should treat a workspace `packages/shared` has no framework-aware ESLint config for, and how to point Vercel at the new build location without touching dashboard-only settings from an agent session.

**Decision.** (1) **Supabase client split:** `packages/shared/src/supabase/client.ts` is a thin `createSupabaseClient(url, key, options)` wrapping `@supabase/supabase-js`'s `createClient<Database>` — genuinely platform-agnostic, since it takes session-persistence strategy as an opaque `options` param. Web's own `client.ts`/`server.ts` (browser/SSR-cookie-aware, via `@supabase/ssr`) and `service-role.ts` stay in `apps/web` unchanged in behavior, just importing the `Database` type from `@matos/shared` instead of defining/duplicating it. The service-role client in particular stays in `apps/web` only, permanently — never reachable from any package `apps/mobile` will also depend on, even indirectly via workspace resolution. (2) **Event taxonomy types** (`PositionRef`/`EventTypeRef`/`PositionRow`/`EventRow`) didn't exist as a shared file before this — they were defined inline in `tagging-screen.tsx` (and duplicated inline again in `tag-edit-dialog.tsx`). Extracted to `packages/shared/src/taxonomy/types.ts`, both call sites updated to import from there — this also deduplicates the two inline copies that already existed pre-restructure, not just relocates one. (3) **lint-staged** narrowed its `eslint --fix` step to `apps/web/**/*.{js,jsx,ts,tsx}` only (was previously a single repo-wide glob, back when the repo root and the Next app were the same directory) — `packages/shared` has no Next-aware ESLint config of its own yet, and standing one up was out of scope for a stage whose own gate is "nothing user-visible changes." `prettier --write` stays repo-wide, since Prettier doesn't need a framework-specific config to resolve. (4) **Vercel:** rather than changing the dashboard's Root Directory setting (an out-of-repo action), added a root `vercel.json` (`installCommand: npm install`, `buildCommand: npm run build --workspace=apps/web`, `outputDirectory: apps/web/.next`) and kept `.vercel/project.json` at the repo root — the directory the Vercel CLI has been invoked from all along this project's history — so the existing project link keeps working with zero dashboard changes.

**Reasoning.** Each of these keeps the "S0 changes nothing user-visible, packages/shared imports neither react-dom nor react-native" constraint as literally true as possible: the client-factory split avoids either (a) forcing Next-specific SSR cookie logic into a package mobile will also import, which would be actively wrong for RN, or (b) pretending a "shared" factory exists when the real value (avoiding type drift) is fully captured by just sharing the `Database` type. The lint-staged narrowing is a scope-appropriate deferral, not a silent gap — flagged here rather than either standing up unrequested new tooling or leaving `packages/shared` files invisible to `eslint --fix` without anyone knowing why. The `vercel.json` approach keeps deployment config in-repo and reviewable rather than requiring an unreviewable dashboard click from an agent session.

**Alternatives considered.**

- _Reimplement `@supabase/ssr`'s cookie-handling logic generically inside `packages/shared` so web and mobile could share one factory call:_ rejected — RN has no cookies at all (Supabase-on-RN uses AsyncStorage/SecureStore via plain `@supabase/supabase-js` options), so a "shared" cookie-aware factory would either be dead code on mobile or would need platform branching inside the shared package itself — more complexity than the thin-wrapper-plus-shared-types split for no real benefit; `@supabase/ssr`'s own `createBrowserClient`/`createServerClient` already are the correct, officially-maintained web-SSR factory, not something worth reimplementing.
- _Set up a minimal root-level ESLint config now so `packages/shared` gets linted too:_ rejected for this stage specifically — right scope for a later stage (or whenever `packages/shared` grows enough files that skipping lint on it becomes a real risk), not this one, whose own gate is regression-only.
- _Point Vercel's Root Directory at `apps/web` via the dashboard instead of `vercel.json`:_ rejected — functionally equivalent, but moves a real config decision out of the repo and into an unreviewable, unversioned dashboard click; `vercel.json` achieves the same build behavior while staying in git history.

### 2026-07-26 — Stage S1: account-primary schema, multi-membership RLS correctness

**Context.** `matos_mobile_plan.md` §2.2 specifies a new `memberships` table (user_id, gym_id, role, joined_at, active) so a user can belong to more than one gym — most immediately, so a solo athlete's personal workspace (`gyms.kind = 'personal'`, §2.1) and a real gym membership can coexist on the same account. But every existing RLS helper function (`private.my_gym_id`, `my_member_id`, `my_role`, `is_coach_or_owner`, `is_owner`) and three trigger-level role guards (`enforce_member_role_insert_guard`/`update_guard`/`enforce_member_self_update_scope`) were written against a hard invariant that no longer holds once this ships: `members.user_id` carried a _global_ unique constraint, so `where user_id = auth.uid() limit 1` was always unambiguous. Relaxing that constraint to per-gym (required for the same account to hold two `members` rows) makes every one of those `limit 1` lookups genuinely ambiguous the moment any user has two memberships, not just theoretically so.

**Decision.** Fixed the ambiguity at the schema gate (this stage), not deferred to Stage S2 (which only owns the UI for switching gyms per the plan's own stage breakdown). Added `memberships.is_current boolean` — not in the plan's literal column list — with a partial unique index (`on memberships (user_id) where is_current`) enforcing at most one current membership per user as a real database invariant, not application discipline. Rewrote the five RLS helper functions to resolve via `memberships where user_id = auth.uid() and is_current` instead of the old unscoped `members` lookup. Added `public.set_active_gym(p_gym_id)`, a SECURITY DEFINER RPC that atomically unsets the old current row and sets the new one after validating the caller actually has an active membership for that gym — the only sanctioned way `is_current` can change (no client write policy on `memberships` touches it at all). Kept `members.role`, not `memberships.role`, as the sole source every permission check reads — `memberships.role` is a denormalised snapshot for future "gyms I'm in" list UI only. Rescoped the three trigger-level role guards to `new.gym_id` (the row being written) rather than the caller's active gym, since a write guard's question is "what's my role in the gym this row belongs to," not "what's my role in whichever gym I currently have selected" — a subtly different scope than the read-path helpers, deliberately not copy-pasted from them. Backfilled one `is_current = true` memberships row for every existing linked `members` row, so every current single-membership user resolves identically to before this migration. Separately, added `breakdowns.visibility` (`private`/`gym`, default `gym`) per §2.2, and discovered while writing the policy update that the two child tables (`breakdown_positions`, `breakdown_events`) had flat gym-scoped SELECT policies with no reference to their parent breakdown's visibility at all — a coach would have been unable to see a private breakdown's own row but still able to see its tagged positions/events directly. Closed via an `exists` join against `breakdowns.visibility = 'gym'` in both child policies, in the same migration, before it could ship as a gap.

**Reasoning.** This stage is explicitly BLOCKING-gated (security-reviewer + database-reviewer) specifically because it changes the foundation every other RLS policy in the app sits on; shipping the schema/column-list part of the plan while leaving the now-ambiguous helper functions unfixed would pass a superficial "does the schema match §2.2" read while leaving a live correctness gap under every existing policy the moment any account gets a second membership — exactly the kind of half-fix the gate exists to catch, so fixing it here rather than waiting for S2 to notice isn't scope creep, it's what the gate is for. Verified live post-migration (not just "applied without error"): a coach and an unrelated-gym athlete were both signed in via real auth sessions post-migration, and each correctly resolved only their own gym's members/memberships/breakdowns through the rewritten helpers — including a same-gym duplicate `(gym_id, user_id)` insert being correctly rejected by the new constraint, confirming the old global-unique constraint was actually dropped and not just shadowed by the new one.

**Alternatives considered.**

- _Defer the helper-function fix to Stage S2, ship S1 as schema-only per the plan's literal column list:_ rejected — S2's own stated deliverable is the _UI_ for switching active gym, not RLS correctness; deferring would mean the BLOCKING gate reviews a migration that is schema-complete but security-incomplete, the exact failure mode the gate is meant to catch before Stage S2 application code ever depends on it.
- _Let `memberships.role` be the authoritative permission-check source going forward, migrating `members.role` reads to it:_ rejected — every existing app code path (RLS policies, trigger guards, the agent's tools, the UI) already reads `members.role`; introducing a second authoritative source this late risks drift between the two, which is a privilege-escalation-shaped bug class, for no correctness benefit `memberships.is_current` doesn't already provide.
- _Scope the trigger-level guards to the caller's active gym (`private.my_gym_id()`), matching the read-path helpers exactly:_ rejected — a guard on an insert/update to a specific `members` row needs to check the actor's role _in that row's gym_, which for a coach mid-switch (or acting via a future admin/cross-gym flow) isn't guaranteed to equal their currently-active gym; `new.gym_id` is the correct scope for a write guard even though it looks like an inconsistency next to the helper functions at a glance.
- _Add a public SELECT-resolution mechanism for `share_links` now, since the table exists in this migration:_ rejected — deferred to Stage S3 deliberately (see the migration's own header notes), which owns the actual public share page and gets its own dedicated security review specifically because it's the app's first genuinely public-facing surface; building the resolution function without that page and review context risks under-scoping what it needs to redact.

**Gate outcome and re-verification.** The BLOCKING gate's first pass on this migration was not clean: both security-reviewer and database-reviewer independently caught the same CONFIRMED/BLOCKED finding — the rewritten helper functions had silently dropped the `and active` filter that `20260716130000_rls_active_member_check.sql` added specifically to stop a deactivated member's still-live auth session from retaining data access (that migration's own header explains why: flipping `members.active` doesn't revoke the Supabase Auth session itself). database-reviewer additionally caught a second CONFIRMED/BLOCKED finding: the live invite-claim route (`api/invite/[token]/claim`) only ever writes `members.user_id`, with nothing populating the new `memberships` table — every new invite claim from this migration onward would have silently produced a user with zero memberships rows (auth works, app renders empty, no error surfaced anywhere). Both were fixed before this migration was considered complete: the five helper functions were rewritten again to join `memberships` to `members` in a single query each (fixing the dropped `active` check and, per a MEDIUM finding, eliminating a redundant nested `my_gym_id()` call inside each of the other four — SECURITY DEFINER functions are never planner-inlined, so the nesting was a genuine double lookup across every one of the dozens of existing policies that compose these functions); a new `members_sync_memberships` trigger now upserts a `memberships` row whenever `members.user_id` is newly set, closing the invite-claim gap at the DB layer rather than patching that one call site. Two more MEDIUM/LOW items from the same passes were folded into the same fix: `set_active_gym()` gained a `pg_advisory_xact_lock` to serialize concurrent calls for the same user (previously a real, if narrow, race against the partial unique index), and a redundant `memberships_user_id_idx` was dropped (already covered by the composite `memberships_user_gym_unique (user_id, gym_id)` index's leftmost prefix). All fixes were re-applied live (via `supabase db query --linked`, not a second migration file, since the original was neither committed nor yet gate-passed) and re-verified both by re-running the full BLOCKING gate (both reviewers passed clean on the second pass) and by direct behavioral test: an active coach's access was confirmed unchanged, then the same coach was deactivated via service-role and confirmed to correctly lose all data access (0 members, 0 gyms visible) — the exact scenario the original fix and this regression were both about.

Both re-verification passes independently flagged the same two LOW/informational items, neither rising to blocking, both explicitly forward-looking rather than current gaps: (1) `members_sync_memberships` only handles the link direction (`user_id` set from null) — if a future flow ever unlinks a user (`user_id` set back to null) or reassigns a member row to a different user, the trigger doesn't clean up the old `memberships` row; harmless today since no such flow exists anywhere in the codebase (the stale row grants no access, since the helper functions require matching `members.user_id`), but worth a deliberate look whenever a future stage first builds an unlink/reassign path. (2) `set_active_gym`'s advisory lock key (`hashtext(auth.uid()::text)`) uses a 32-bit hash, so two unrelated users could theoretically collide into the same lock bucket — a pure lock-contention/performance nit (the actual one-current-membership invariant is still enforced independently by the partial unique index regardless), not a security concern, and not worth the complexity of a wider key unless this RPC ever sees meaningful concurrent traffic.

### 2026-08-04 — Stage S2: account-primary features (signup, attach flow, switcher, solo deletion, breakdown visibility)

**Context.** `matos_mobile_plan.md`'s build-sequence table describes S2 as: "Web: solo signup + personal workspace creation, attach flow for existing accounts, context switcher, self-serve deletion, breakdown visibility toggle + coach-visibility enforcement," gated on **all reviewers** (unlike S0's code-reviewer-only gate or S1's security+database-only gate). Before writing any code, two genuinely ambiguous product-scope questions were confirmed with the user rather than guessed: (1) what a solo user actually sees on web after signup, given the plan itself frames mobile as the real solo-athlete product ("Coach experience stays on web for v1"); (2) how self-serve immediate deletion should handle a user who has _both_ a personal workspace and a real gym membership, given the tension between "immediate, no approval needed" (the Apple/GDPR requirement this feature exists to satisfy) and Rule 6's existing coach-approved anonymisation flow for gym-context data. Both were resolved in favour of the narrower, more conservative option: web gets a minimal Analysis+teaser landing (not a bespoke solo dashboard — mobile owns that), and self-serve deletion is solo-only, blocking with a clear message for any user who also belongs to a real gym.

**Decision — scope discovered mid-build, not in the plan's literal wording.** Research before writing code surfaced a real, load-bearing bug the plan didn't anticipate: `withAuth` and `getCurrentMember()` (and, found via a follow-up grep, five more client-side pages) all resolved "the caller's member row" via `.eq("user_id", user.id).single()` against `members` — correct back when that column was globally unique, but S1 made it possible for an account to hold two `members` rows (a personal workspace plus a real gym), which makes `.single()` throw the moment any user actually has both. This wasn't hypothetical or deferred — S2's own signup+attach flows are exactly what makes the scenario real, so every authenticated page load and API route would have started breaking for that population the moment S2 shipped without a fix. Closed with a new migration (`20260803120000_current_member_rpc.sql`) adding `public.current_member()` — a SECURITY INVOKER RPC delegating to the already-reviewed `private.my_member_id()`, PostgREST-exposed (unlike the `private.*` schema) so application code has one authoritative resolution path instead of seven independently-duplicated ones. All seven call sites were rewritten to use it.

**Decision — attach flow proves ownership via a real sign-in, not a bare email match.** The plan describes the attach flow only as "user accepts in-app" — under-specified enough that a naive implementation (link based on email match alone) would be a straightforward account-takeover: anyone who obtained an invite token sent to an email that happens to already have a MatOS account could claim that account without ever proving they control it. The claim route instead determines server-side (via `find-user-by-email.ts`, never trusting a client-supplied flag) whether the invited email already has an `auth.users` row, and if so requires the _existing_ password, verified by actually attempting `signInWithPassword` against a throwaway anon-key client — genuine proof of ownership, reusing infrastructure rather than inventing a new verification primitive. The GET `/api/invite/[token]` route's new `accountExists` field (letting the claim UI pick the right form before submission) only discloses account existence to someone who already possesses a valid, unclaimed, unexpired invite token for that specific email — scoped, not a general enumeration oracle.

**Decision — solo deletion anonymises the personal `gyms` row rather than hard-deleting it, contradicting the plan's own literal wording.** The plan says self-serve deletion should leave the "personal workspace and all contents hard-deleted." This is schema-impossible: `audit_log.gym_id` is `not null references gyms(id) on delete restrict`, and audit_log is immutable by design (a trigger blocks DELETE even for the service-role client, per Rule 6) — every personal workspace has at least one audit_log row from the moment it's created (the signup itself writes one), so the `gyms` row can never actually be deleted, full stop, regardless of how the route is written. The route instead hard-deletes everything that has no such constraint (breakdowns and their positions/events, gdpr_consents, the `members` row, the `auth.users` row itself) and anonymises the `gyms` row in place (name, contact_email, address, logo_url stripped; `active = false`) — matching the exact same anonymise-not-delete precedent the existing coach-executed GDPR route already established for `members`, applied here to `gyms` for the same structural reason.

**Gate outcome and re-verification.** The all-reviewers gate (security, database, code, run in parallel) was not clean on the first pass — the first attempt at all three stalled on a transient infrastructure issue (no findings produced, not a real result) and was retried successfully. database-reviewer returned the pass's one BLOCKED finding: `delete-solo`'s deletion sequence only cleared `breakdowns` and `gdpr_consents` before attempting to delete the `members` row, missing six more `on delete restrict` FKs anchored on `members.id` (`belt_history`, `attendance`, `payments`, `athlete_logs`, `invites`, `deletion_requests`) — and the gap was concretely reachable, not theoretical: none of `/api/logs`, `/api/payments/record`, or `/api/members/[id]/promote` gate on `gymKind`, and a solo signup grants `role: gym_owner`, which satisfies every `requiredRole: "coach"` check in the app. A solo user who'd ever logged a self-note, recorded a payment on themselves, or self-promoted their belt would hit an unhandled FK violation mid-deletion — by which point `breakdowns`/`gdpr_consents` were already irreversibly gone, leaving the account semi-deleted with no rollback. Fixed by extending the route to delete all six tables (scoped by `member_id`) before the `members`/`gyms` steps — hard-deleted rather than anonymised, since a personal workspace has no "gym business records" to preserve the way the coach-executed route's anonymise-in-place approach protects for a real gym. Re-verified live: created a real row in every one of the six previously-missed tables for a fresh solo test account, ran the actual UI deletion flow, confirmed every row (plus the member and auth user) was gone afterward with zero errors — then re-ran database-reviewer specifically against the fix, which confirmed it complete against the authoritative FK graph (re-derived independently, not just re-reading the restated list) and confirmed the ordering within the six-table loop is genuinely order-independent (none of the six reference each other).

The same gate pass also surfaced three lower-severity, non-blocking findings, all fixed in the same round rather than deferred: (1) `signup`'s rollback correctly ordered `members` before `gyms` on the `members.gym_id on delete restrict` FK, but didn't account for the _newer_ `memberships.gym_id on delete restrict` FK — the S1 `members_sync_memberships` trigger creates a `memberships` row the instant the `members` insert succeeds, so the one rollback path that runs after that insert (a `gdpr_consents` failure) would have failed silently on the `gyms` delete, since none of `rollback()`'s three steps checked their own errors; fixed by explicitly deleting `memberships` first and logging every step. (2) The claim route's `rollbackAttachLink()` had the same silent-failure shape — if either of its two writes failed, an otherwise-unaffected multi-workspace user could be left with zero `is_current` rows and no trace to debug from; fixed by logging both. (3) `account/page.tsx`'s own `hasRealGymMembership` check queried `memberships` without the explicit `.eq("user_id", ...)` filter that a _sibling_ function (`getUserGymMemberships()`, in `current-member.ts`) had already been fixed to add earlier in the same build session, for the same reason: `memberships_select_staff` deliberately lets a coach/owner read every member's `memberships` row in their own gym, not just their own, so an unfiltered query risks pulling in coworkers' rows. Both security-reviewer and code-reviewer independently flagged this same inconsistency; fixed for parity. A fourth, cosmetic-only finding (a code comment asserting `breakdowns.author_id` was still `on delete restrict`, when `20260723190000` had already relaxed it to `on delete set null`) was corrected to match reality. Re-deriving the FK graph for the BLOCKED-finding re-verification also surfaced one adjacent, previously-unflagged gap: `POST /api/members` didn't gate on `gymKind` either, meaning a personal-workspace owner could in principle add extra member rows to their own "gym" via direct API call (no UI path reaches it) — silently violating the single-member invariant `delete-solo` and other S2 design decisions assume. Fixed with the same guard pattern.

**Reasoning.** Every deviation from the plan's literal wording here was a genuine schema/security constraint discovered by reading the actual FK graph and RLS policies, not a preference — the plan's own methodology line ("staged build, ECC gates, security-reviewer + database-reviewer BLOCKING on all schema/RLS changes") exists precisely so these get caught before Stage S3/mobile work depends on them, and the BLOCKED finding here is a clean example of the gate doing its job: a solo signup+deletion path that would have looked complete under the plan's own literal description but silently corrupted itself the first time real usage (a self-recorded payment, a self-note) touched it.

**Alternatives considered.**

- _Link the attach flow purely on email match, no password verification:_ rejected outright — a straightforward account-takeover vector; explicitly checked and confirmed sound by the security-review pass instead.
- _Defer the `current_member()` RPC fix to whichever future stage first hits the ambiguous-query bug in practice:_ rejected — S2's own signup+attach flows are what make an account holding 2+ `members` rows a real, everyday occurrence for the first time, not a future hypothetical; shipping S2 without fixing this would have broken authenticated page loads for exactly the population the stage exists to serve.
- _Gate `/api/logs`, `/api/payments/record`, `/api/members/[id]/promote`, and other gym-context routes against `gymKind === 'personal'` instead of (or in addition to) completing `delete-solo`'s own deletion sweep:_ noted as "the more defensible product decision" by database-reviewer but deliberately not taken here — it's a broader, unilateral scope decision about what personal workspaces should be _allowed to do_ generally, not just what `delete-solo` needs to _handle_; completing the deletion sweep closes the actual BLOCKED finding without deciding that larger question on the gate's own authority. `POST /api/members` was the one exception, gated directly — narrower in scope (prevents violating a single-member invariant several other design decisions already assume) rather than a general "restrict solo capabilities" policy call.
- _Leave the three lower-severity rollback/consistency findings for a follow-up pass, since none were individually BLOCKED:_ rejected — matches this session's established practice (identical to S1's gate) of fixing everything a BLOCKING gate surfaces in the same round when the fixes are cheap and correctly scoped, rather than re-opening the same gate a second time for issues already identified once.

### 2026-08-04 — Stage S3: public share pages (the app's first unauthenticated surface)

**Context.** `matos_mobile_plan.md`'s build sequence describes S3 as "Web: public share pages (profile card / breakdown, token-resolved, redaction default) + share image generation," gated on a dedicated security review specifically because it's "the first public surface." The `share_links` table itself shipped in S1 with a `redact_opponents` column, but S1's own design notes deliberately left _what it actually redacts_ undecided — the schema has no per-match "opponent" field at all (confirmed by research before writing any code: `breakdowns` never had one, an `opponent_name` column existed briefly on the old, since-deleted `analyses` stub and was dropped when that approach was scrapped). The only place a real third party's identity can appear as the _subject_ of a share is an `external_people` row (someone tagged from scouting footage who never consented to being public) — so `redact_opponents` was implemented as "replace that person's real name with a generic label," not "hide opponent identity within a match," which doesn't exist as a concept to hide.

**Decision — public resolution reuses the invite flow's established pattern, not a new SQL security-definer function.** S1's own design note phrased public token resolution as needing "a security-definer function" — read literally, that could mean a new Postgres RPC. Built instead as a Next.js route (`lib/share/resolve-share-link.ts`) using the service-role client, hashing the incoming token and looking up `share_links` directly — exactly mirroring the already-reviewed `GET /api/invite/[token]` route, which has followed this exact shape since Stage 3. `share_links` and every table it points at correctly have **no public RLS policy at all** (the actual requirement S1's note was protecting), so the "new SQL function" framing was one possible implementation of that requirement, not the requirement itself; reusing proven, already-reviewed infrastructure over introducing a second, parallel public-resolution mechanism was the more defensible choice.

**Decision — creation authorization reuses RLS as the authorization boundary, rather than reimplementing ownership logic.** `POST /api/share-links` decides whether a caller may share a given `subject_id` by attempting an RLS-respecting read of it (a `members`/`external_people`/`breakdowns` row) and allowing creation only if that read succeeds. This can't grant access to anything the caller couldn't already reach in-app — sharing is a strictly smaller capability than viewing — and it means the creation route never has to know or duplicate the actual RLS policy shapes (`breakdowns_all_own`, `external_people_all_staff`/`_all_self`, etc.), which stay the single source of truth. Security-reviewer confirmed this pattern sound and confirmed it fails closed (a query error is indistinguishable from "not found," both correctly block creation).

**Gate outcome — one CRITICAL/BLOCKED finding, caught exactly where the gate exists to catch it.** Security-reviewer found that `resolve-share-link.ts` called the existing, already-reviewed `fetchAthleteProfileData()` (extracted at Stage A7, shared by the authenticated profile view and the agent's read tools) with a **service-role client** — the first caller to do so. That function's whole safety contract, stated in its own header comment since A7, is that RLS scopes which breakdowns get aggregated, not the function itself; a service-role client bypasses RLS entirely. Concrete impact: a public profile share would have silently folded `visibility: 'private'` breakdowns into the public aggregate stats — data not even the breakdown's own subject or other gym staff can see in-app, now readable by anyone with the link. Fixed by adding an explicit `publicVisibilityOnly` option to `fetchAthleteProfileData()` (only `resolve-share-link.ts` passes it; both existing authenticated call sites are untouched, byte-identical behavior), applying `visibility = 'gym'` at the query level rather than trying to reconstruct a hypothetical viewer's full RLS view. Re-verified live: seeded a real `private` breakdown, confirmed a public share's match count didn't move, then flipped it to `gym` visibility and confirmed the count updated on the very next request — then re-ran security-reviewer specifically against the fix, which confirmed it complete and confirmed the doc comments now actively guard against a future third call site repeating the mistake.

**A second, related bug surfaced during that same live re-verification, not by either reviewer:** even with the visibility filter correctly applied, the public page kept serving stale data on repeat requests to the same token, traced to Next.js's request/data-fetch cache still caching the underlying Supabase REST calls despite the page already having `export const dynamic = "force-dynamic"` (which disables the _route's_ static-HTML cache, not individual `fetch()` calls made from within it). Fixed with `unstable_noStore()` — Next's documented, more granular API for exactly this — called once at the top of `resolveShareLink()` itself, ahead of every branch, so it covers all three share-resolution paths (member profile, external-person profile, breakdown) with a single call rather than needing one per branch. This mattered directly for the BLOCKED finding too: a stale-cache bug on this function would have meant even a _correctly_ filtered result could keep being served after data changed — undermining the guarantee that revoking a link, or a breakdown's visibility changing, takes effect immediately. Re-verified live (repeat requests after data changes returned fresh results, and a revoked link stopped resolving on the very next request) and re-confirmed by the same security-reviewer pass as sufficient and correctly scoped.

**Other findings, all non-blocking, all fixed in the same round:** code-reviewer found the condensed public profile card dropped every metric's `n` — a direct regression against the Match Analysis Module's own Non-Negotiable #6 ("every metric renders its n"), and arguably worse to drop on the one page a stranger might see with zero other context; fixed by mirroring `ProfileView`'s existing `MetricRow` pattern exactly. Also fixed: submission-type badges showed raw taxonomy codes (`heel_hook`) instead of the humanized labels the authenticated profile view already applies via the existing `humanize()` helper; the gi/no-gi "which style has more matches" tie-break logic was independently copy-pasted three times across two files with no shared source of truth, consolidated into one exported `pickPrimaryStyle()` helper; the share page's `<meta>` description was a static, always-wrong string for profile shares ("A BJJ match breakdown..." on a page that's never a breakdown), converted to `generateMetadata()` resolving the actual token; the external-person profile page had a fully-implemented, RLS-gated share code path with no UI button to reach it, so it was untested by anything — wired in rather than left dead; and the account page's share-links list silently rendered identically for "you have no share links" and "the fetch failed," given a distinct error state matching the same file's own established pattern one component above it.

**Reasoning.** The BLOCKING security gate on this stage is explicitly named in the plan as extra scrutiny for "the first public surface" — the finding it caught (a service-role client silently bypassing a data-visibility rule an existing, previously-reviewed function was never designed to defend against on its own) is precisely the kind of cross-cutting regression that's easy to miss reading either file in isolation and easy to catch when a security review is specifically looking for "what changed about who can call this, and does its safety contract still hold." The caching bug is a reminder that "live-verify, don't trust a check without confirming" has to include _re-verifying after a data change_, not just confirming a page renders once — the first version of this stage's own live testing would have reported success on a page that was, underneath, silently serving stale results.

**Alternatives considered.**

- _Fix the visibility gap by trying to reconstruct "what a hypothetical authenticated viewer would see" (e.g., pass a synthetic role/gym context into the aggregation) rather than a flat `visibility = 'gym'` filter:_ rejected — a public share has no single "viewer" to reconstruct RLS for; the flat filter matches the actual, simple safety property that matters ("never surface private data publicly"), and is auditable at a glance rather than requiring trust in a more elaborate simulated-permissions calculation.
- _Add the `publicVisibilityOnly` filter unconditionally to `fetchAthleteProfileData()`'s default behavior, closing the gap for every possible future caller at once:_ rejected — this would silently change the _existing_, already-reviewed authenticated profile view's behavior (which correctly includes a user's own authored breakdowns regardless of visibility, per Stage A7's RLS model), a real regression to trade for closing a gap that only exists for a caller supplying a non-RLS-respecting client — better closed by making that one caller opt in explicitly, which the fix does.
- _Only add `export const dynamic = "force-dynamic"` and treat that as sufficient, without also adding `noStore()`:_ this is what the first fix attempt did, and it demonstrably wasn't sufficient — caught by live re-testing before it could ship, not assumed correct because the route-level flag existed.

### 2026-08-04 — Stage M0: Expo mobile scaffold, npm-workspace React 18/19 dependency isolation

**Context.** Stage M0 (`matos_mobile_plan.md`'s build sequence: Expo scaffold, NativeWind + design tokens, EAS config, Supabase client with RN session persistence, expo-router navigation shell, auth screens) is the first stage that touches `apps/mobile` at all. `apps/web` needs React 18 (Next.js 14.2.35 doesn't support 19); Expo SDK 57 requires React 19.2.x. A conflicting-version monorepo like this has no single correct npm-workspaces answer out of the box — npm has no Yarn-style `nohoist`, and which React version wins the hoist race to the shared root `node_modules` is not fully deterministic across installs (observed directly during this stage: three consecutive clean reinstalls, differing only in whether `package-lock.json` was deleted first, produced three different outcomes for what ended up at the workspace root).

**Decision.** Root `package.json` now explicitly declares `react`/`react-dom` (dependencies) and `@types/react`/`@types/react-dom` (devDependencies) pinned to the exact versions `apps/web` needs (18.3.1 / 18.3.31 / 18.3.7). This isn't the root app depending on React for its own sake — it's the mechanism that deterministically wins npm's hoisting decision, so root always resolves to 18.x and `apps/web`'s own third-party dependencies that get hoisted to root (Radix UI primitives, in practice) reliably see the same React their own nested `apps/web` code uses. `apps/mobile`'s conflicting `~19.2.2` requirement is thereby always forced to nest its own copy, which is the arrangement that works cleanly — confirmed by three-way `tsc --noEmit` across `apps/web`, `apps/mobile`, and `packages/shared` plus a full `apps/web` production build, all clean, after this pin. A root-level `overrides` block additionally pins `react-native-reanimated`/`react-native-worklets` to the exact Expo-SDK-compatible versions `apps/mobile` itself declares — without this, `react-native-css-interop` (nativewind's runtime CSS-interop dependency) auto-installs its own slightly-newer peer versions of both, which drags a second, divergent private copy of React itself along with it. `apps/mobile/metro.config.js`'s explicit `resolver.nodeModulesPaths` (needed for the monorepo layout generally, so Metro can find hoisted packages and `@matos/shared`) also gained an explicit entry for `nativewind`'s own nested `node_modules` — nativewind's `react-native-css-interop` dependency still legitimately nests there whenever root's React version doesn't satisfy it (i.e., always, given the 18-pin above), and an explicit `nodeModulesPaths` list replaces Metro's default per-file hierarchical directory walk rather than extending it, so without this entry that nested copy is unreachable at runtime even though it resolves fine at the filesystem level.

**Decision — `apps/mobile/tsconfig.json` does not set `jsxImportSource: "nativewind"`.** NativeWind's own setup docs suggest this, and it was tried first — but doing so makes every `.tsx` file's JSX type-checking resolve through nativewind's own `jsx-runtime.d.ts`, which re-exports `react/jsx-runtime` types from **nativewind's own physical location** (hoisted to root or its own nested subtree), not from `apps/mobile`'s own nested React — producing exactly the "two different React type universes" collision (`Type 'bigint' is not assignable to type 'ReactNode'`) that a same-file, same-version React 18/19 mismatch produces. `"jsx": "react-jsx"` alone (no `jsxImportSource` override) makes TypeScript resolve the JSX namespace from whichever React `apps/mobile`'s own code already imports, which is correct. NativeWind's `className` prop typing (needed regardless, since `"jsx": "react-jsx"` alone doesn't add `className` to `View`/`Text`/etc.) is instead hand-written directly in `apps/mobile/nativewind-env.d.ts` — a local `declare module "react-native" { interface ViewProps { className?: string } ... }` block covering exactly the props MatOS's own screens use — rather than relying on nativewind's own `nativewind/types` → `react-native-css-interop/types` reference chain, which has the identical physical-location problem: it augments react-native _as resolved from nativewind's own nested copy_, a different module identity than the react-native `apps/mobile`'s own code imports, so the augmentation silently doesn't apply. This local file is intentionally small and manually maintained (not "the right long-term answer" in the abstract) but is fully decoupled from wherever nativewind's own dependency chain happens to physically resolve on any given install — which, per the above, is not guaranteed stable across reinstalls.

**Reasoning.** Every one of these fixes traces back to the same root cause (two npm-hoisted React copies, and packages resolving types/runtime modules from whichever physical copy happens to be nearest to _their own_ location rather than the app's) — fixing it structurally at the npm-hoisting level (the root pin) rather than only patching each individual downstream symptom (the tsconfig/metro/nativewind-env fixes) was necessary because the downstream symptom list is not closed — a fourth clean reinstall with a different hoisting outcome could easily have surfaced a fifth variant of the same class of bug in some other nativewind-adjacent or Radix-adjacent package. The root pin doesn't make the underlying two-React-versions situation go away (it structurally can't, given `apps/web` and Expo SDK 57's real constraints) — it makes _which_ npm hoists where deterministic, which is what actually matters for reproducibility across machines and CI.

**Gate outcome.** M0's own build-sequence row calls for a code-reviewer-only gate (no schema/RLS work in this stage). One HIGH finding: the `(auth)` route group's blanket "redirect to `/` if already signed in" rule (correct for `login`/`signup`) also applied to `invite/[token]`, silently breaking the attach flow's actual primary scenario — a user already signed in on this device tapping a coach's `matos://invite/<token>` deep link to link a second gym to their existing account, per Stage S2's attach-flow design. Fixed by checking `usePathname()` in the layout and skipping the redirect specifically for the invite route. Three MEDIUM findings, all fixed in the same round: `apiPost`/`apiGet` (`apps/mobile/src/lib/api.ts`) had no try/catch around `fetch()`/`res.json()`, so a phone going offline mid-submit threw past every call site with no user-visible error — wrapped both in try/catch returning a generic network-error `ApiErrorBody`; `font-medium`/`font-semibold` NativeWind classes across all four screens rendered as regular weight on-device, since React Native doesn't synthesize a heavier weight from a single embedded TTF the way a browser synthesizes `font-weight` from one `@font-face` — fixed by adding a `sans-bold` (→ `Inter-Bold`) font-family utility and switching every such usage to it, matching RN's actual font-selection model (family, not synthesized weight); no CORS headers exist on `apps/web`'s `/api/signup`/`/api/invite/[token]/claim` routes, so this stage's `expo start --web` verification could not itself exercise those two POST flows against a real deployed backend (native iOS/Android builds are unaffected — CORS is browser-only) — logged here rather than silently worked around or fixed unilaterally, since adding CORS headers is a real change to `apps/web`'s public-facing security surface and deserves its own explicit decision, not one bundled into a mobile-scaffold stage. ### 2026-08-05 — Stage M3: native tagging player (mobile), local-first offline draft model

**Context.** M3 (build sequence: "Native tagging player — video player, category rail, tagging overlay, timeline, undo, offline draft/sync") is the mobile plan's headline feature and the one stage explicitly gated on **all three reviewers** ("the core interaction"), matching this project's own precedent for the highest-stakes stages (S1, S2, M1's bearer-token mechanism). Web's `tagging-screen.tsx` has no offline mechanism at all — every tag action is an immediate, awaited server round-trip — so mobile's own offline requirement (`matos_mobile_plan.md`: "All tagging state in a local draft file; server sync is explicit save and auto-sync when online") had no existing pattern to port and needed a genuinely new design.

**Decision — local-first draft architecture: every tag write lands in a local file first, a background engine syncs it to the same existing web API routes.** `apps/mobile/src/lib/tagging-draft.ts` is the single source of truth for an active tagging session (the UI never re-fetches `breakdown_positions`/`breakdown_events` mid-session, only hydrates once on first open); `apps/mobile/src/lib/tagging-sync.ts` opportunistically pushes queued create/update/delete operations to the exact same routes web's own tagging screen and M1/M2's mobile writes already use — not the `tag_position` RPC directly — keeping error mapping and audit-log behavior identical across platforms (the established pattern since M1's check-in flow). Position creates sync strictly in array/tap order, one at a time, since `tag_position`'s "close whatever's open" logic depends on reconstructing the same interval chain regardless of how long a device was offline; a failed position sync stops that queue entirely rather than skipping ahead, while events (no interval semantics) sync independently and keep going past individual failures.

**Decision — golden-rule timestamp capture, Mode 1/Mode 2 split, and the rest of the tagging UX exactly mirror `matos_tagging_ux_plan.md`.** Category rail (5 categories + Position, auto-fades after 3s idle), tap-to-tag with immediate confirm for roleless positions, undo toast (4s, doesn't pause video), and the timeline demoted to a tap-to-expand sheet all match the U-plan's contract; landscape-lock on entry with portrait restored on exit (root `_layout.tsx` owns the app's default portrait lock; this screen is the one deliberate override) since RN has no web-style fullscreen-container constraint to work around.

**Gate outcome — three reviewers, one CRITICAL, several HIGH, all fixed in the same round before commit (established practice: never piecemeal, never deferred).**

- **CRITICAL (database-reviewer, live-reproduced not just theorized):** neither `breakdown_positions` nor `breakdown_events` creates were idempotent, and nothing prevented two `syncBreakdownDraft` passes from running concurrently for the same breakdown — reachable via ordinary use (a quick double-tap, a reconnect-triggered sync overlapping a confirm-triggered one, or simply a POST whose response is lost after the server already committed, common on mobile). Two independent successful `tag_position` calls for "the same" tag produce a genuine phantom row: the second finds the first's row "open" and closes it (often at the same `start_ts`, satisfying every existing CHECK/unique constraint), silently corrupting profile-metric aggregation (Non-Negotiable #6) with an interval invisible to the device but permanently present server-side. Fixed with two complementary changes, both required (the reviewer's own analysis: neither alone is sufficient): (1) a new migration (`20260805180000_tag_idempotency_keys.sql`) adding a `client_id uuid` column to both tables (the local draft row's own `localId`, already generated client-side the instant a tag is created, reused as the idempotency key), unique-indexed per breakdown, with `tag_position` checking for an existing `client_id` first and returning the original row as a safe no-op on replay — `breakdown_events`' create route does the equivalent check-then-insert itself, since it has no RPC of its own; (2) an in-flight-sync guard in `tagging-sync.ts` coalescing concurrent `syncBreakdownDraft` callers onto a single pass per breakdown, with a trailing-rerun (not plain dedup) so a mutation that lands mid-pass isn't silently swallowed until some unrelated future trigger. **A genuine bug was found and fixed while wiring the migration**: `create or replace function` does not replace a function whose parameter list differs — adding `p_client_id` created a second, distinct 5-arg overload rather than replacing the original 4-arg `tag_position`, silently leaving the old (no-idempotency-check) version live and independently callable alongside the new one. Caught immediately by re-running `supabase gen types` and finding the generated type had become a two-member union; fixed with an explicit `drop function if exists public.tag_position(uuid, uuid, text, numeric)` added to the same uncommitted migration and re-applied live. Live-verified end to end against the real remote DB (not a local Docker instance — unavailable in this environment; applied via `supabase db push --linked` using the project's own access token from `apps/web/.env.local`, the same mechanism prior stages' "`supabase db query --linked`" fixes used): a disposable test breakdown had the same `client_id` submitted to `tag_position` twice — confirmed identical row returned both times, no duplicate — then a genuinely different `client_id` confirmed normal close-and-open behavior was untouched; a parallel test on `breakdown_events` confirmed the unique index independently rejects a raw duplicate insert (23505, already mapped to a clean 409 by the existing `mapBreakdownTagError`). Both disposable breakdowns deleted after verification.
- **HIGH (security-reviewer):** no `canEdit` gate on the video-picker button or "Start tagging" navigation in the breakdown detail screen, and no author check in the tagging screen itself — combined with draft files namespaced only by `breakdownId` (see below) and the sync engine's stop-on-first-failure design (required for ordering correctness), a non-author on a shared-gym breakdown could open the real player and generate local tags that would permanently fail to sync (RLS-rejected), silently blocking that device's draft. Fixed with the same `canEdit` pattern already used for Edit/Delete on the same screen (`breakdown.author_id === member.userId`), applied to both the video-picker button and the "Start tagging" section; a defense-in-depth author check was also added directly in the tagging screen (redirects back via `router.back()` if a direct/deep link reaches it with a mismatched author) — RLS was never the gap here (every write is still independently authorized server-side regardless), but a non-author reaching the screen at all was the actual problem being closed.
- **HIGH (security-reviewer):** local draft files were keyed only by `breakdownId`, with no per-account scoping and nothing clearing them on sign-out — on a shared device, a second account signing in could see, resume, or even sync the first account's in-progress local tags. Fixed by namespacing `tagging-draft.ts`'s file path by the current user id (resolved via `supabase.auth.getSession()`, a local cache read, not a network call) and adding `clearCurrentUserDrafts()`, called from `account.tsx`'s sign-out handler before `supabase.auth.signOut()` (must run while the session is still valid, since it needs the current user's id) as a best-effort step that never blocks sign-out itself on failure.
- **HIGH (security-reviewer):** `syncError` was captured on every draft row but never rendered anywhere in the UI — a stuck sync was undiagnosable without reading source. Fixed in `timeline-sheet.tsx`: rows with `syncStatus === "error"` now show the actual error text beneath the tag label, not just "· unsynced".
- **HIGH (code-reviewer, confirmed not hypothetical):** the undo toast's delete logic searched for "the most recently added row with `pendingOp === 'create'`" rather than using `UndoState`'s own `localId` field (which existed but was populated with the wrong value — the taxonomy reference id, not the draft row's real id — and never actually read). Since every confirm handler fires `sync()` unawaited immediately after showing the toast, and a sync round-trip routinely completes well under the 4-second undo window, the row's `pendingOp` flips to `null` (synced) before the window closes — at which point the heuristic's search finds nothing, undo silently no-ops, and the toast still dismisses as if it worked, leaving the tag permanently in the breakdown. Fixed by capturing the row `addEventTag`/`addPositionTag` actually return, storing its real `localId` in `UndoState`, and having `handleUndo` delete by that id directly — `deletePositionTag`/`deleteEventTag` already correctly handle both the not-yet-synced and already-synced cases, so the heuristic wasn't needed at all.
- **HIGH (code-reviewer, confirmed via a working sibling implementation in the same codebase):** `openTaggingMode`'s timestamp capture read `currentTime`, React state fed by `useEvent(player, "timeUpdate", ...)` which only updates once per `player.timeUpdateEventInterval` (set to 0.25s) — meaning the value read at tap time could lag the real playback position by up to ~250ms, a direct regression against the plan's own framing of accurate timestamp capture as "the single most important behavioural rule." Web's `tagging-screen.tsx` (line 358) already solves this correctly, reading `videoRef.current?.currentTime` first and falling back to state only if unavailable. Fixed by reading `player.currentTime` directly (proven synchronously accessible elsewhere in the same file, via `video-controls.tsx`'s seek handler) in both `openTaggingMode` and the Finish action's own open-interval-close logic, which had the identical pattern.
- **LOW (code-reviewer):** `undoTimer`'s `setTimeout` had no unmount cleanup — harmless under React 18 but inconsistent with `category-rail.tsx`'s own `idleTimer` cleanup in the same review scope. Fixed with a matching cleanup effect.
- **MEDIUM (code-reviewer, not a defect — an honest verification-gap flag):** orientation-lock survival across an iOS background/foreground cycle can't be verified from source or `expo start --web` alone; every code path traced (back button, modal close, backgrounding) looked correct, but this class of bug is a known real-world gotcha for RN orientation libraries specifically under app-lifecycle transitions. Logged, not fixed as a defect, since none was found — flagged for an actual on-device test before this ships broadly, matching the same honesty precedent as every prior stage's native-only verification gaps.
- **LOW (security-reviewer, deferred, not fixed):** local draft JSON is unencrypted and not explicitly excluded from iOS device backups. Lower severity since the file only contains opaque taxonomy ids/timestamps, not names — and unlike the CRITICAL/HIGH items above, no reasonable low-cost fix exists in the current `expo-file-system` API surface (no documented backup-exclusion option was found; moving the draft off `Paths.document` to `Paths.cache` would trade this for a worse problem, since the OS can purge cache at any time and silently lose an in-progress tagging session). Logged rather than worked around with something riskier for a LOW-severity finding.

**Reasoning.** The CRITICAL finding is exactly the kind of gap this stage's all-reviewer gate exists to catch — a concrete, everyday-reachable mechanism for silent data corruption in the one table Stage A3 already hardened once specifically to prevent silent loss (`tag_position`'s own atomicity fix). Both halves of the fix were necessary, not redundant: the in-flight guard closes the double-tap/reconnect-overlap trigger but not the ambiguous-lost-response-then-retry case (per the reviewer's own analysis), while the idempotency key alone doesn't stop two genuinely concurrent local passes from both reading stale pre-sync state. Doing the migration inside this same gate round (rather than deferring, as the database-reviewer's own scope note flagged it might need to be) matches this project's established S1 precedent exactly: a BLOCKING/all-reviewer gate on foundational correctness work is where this kind of fix belongs, not a follow-up stage.

**Verification.** Same honestly-scoped approach as M0–M2: no native simulator/device available, `expo start --web` plus compiled-bundle content checks (`Start tagging`, `client_id`, `clearCurrentUserDrafts`, `unsynced`, etc. all confirmed present in the actual dev bundle output post-fix). `tsc --noEmit` clean across all three workspaces both before and after the gate-fix round; `apps/web`'s production build unaffected (confirmed after this stage's route/schema changes, unlike M2 which touched no web files at all). The idempotency migration was live-verified against the real remote database via disposable test fixtures (created and deleted within this session), not assumed correct from the SQL alone — see the CRITICAL finding above for the specific test sequence.

**Alternatives considered.**

- _Coalesce concurrent `sync()` calls with a plain "return the existing in-flight promise, drop the new call" guard, no trailing rerun:_ rejected — a mutation that lands while a pass is already running would then go unsynced until some unrelated future trigger (the next tag, a reconnect event, or the Finish action's own flush) rather than being picked up promptly; the trailing-rerun version costs one extra `while` check and closes that gap completely.
- _Fix the phantom-row bug with only the idempotency key, treating the in-flight guard as a nice-to-have:_ rejected — the database-reviewer's own analysis showed the ambiguous-timeout-then-retry path reaches the same corruption independent of any concurrency bug, so the key is necessary regardless; but leaving concurrent passes possible means two passes can still both observe the same stale pending row before either writes back, so the guard is equally necessary — neither one alone is a complete fix.
- _Encrypt local draft files or move them to `Paths.cache` to close the LOW backup/encryption finding:_ rejected — no cheap encryption primitive is readily available in `expo-file-system`'s current API without meaningfully more scope, and `Paths.cache` trades a low-severity confidentiality gap for a correctness one (OS-initiated cache eviction silently destroying an in-progress tagging session); logged as a deliberate non-fix rather than reached for a worse tradeoff to close a LOW item.

### 2026-08-05 — Stage M4: in-app recording (mobile), code-reviewer gate

**Context.** M4 (build sequence: "In-app recording → tagging pipeline") adds `matos_mobile_plan.md` §3.2's second video source — "gallery selection AND in-app recording (record a roll → tag immediately)" — alongside Stage M2's existing gallery-pick flow. Code-reviewer-only gate per the plan's own M4 row, since this stage touches no schema/RLS/auth surface.

**Decision — `expo-camera`'s own in-app `CameraView`, not `expo-image-picker`'s native-camera-launch path.** `expo-image-picker` (already a dependency since M2) has its own `launchCameraAsync`, which hands off to the OS's native camera app rather than an in-app view — cheaper to wire but incompatible with the plan's own framing ("record a roll → tag immediately," implying a captured clip flows straight back into the app's own tagging pipeline without a context switch to a separate app). `expo-camera`'s `CameraView` (a fullscreen custom-UI component with `mode="video"`, ref-based `recordAsync()`/`stopRecording()`) matches this directly. `expo-image-picker`'s own `cameraPermission`/`microphonePermission` config stayed `false` (as Stage M2 set them, since the plan's own comment already anticipated recording as later scope) — that plugin's camera path is still genuinely unused; `expo-camera` declares its own separate `NSCameraUsageDescription`/`NSMicrophoneUsageDescription`/`RECORD_AUDIO` permissions in `app.json`, with honest purpose strings now that the app actually captures video (matching §3.4's "honest permission strings" store-compliance line).

**Decision — recorded duration is measured client-side (`Date.now()` start/stop), not read from video metadata.** `expo-camera`'s `recordAsync()` resolves with only `{ uri }` — no duration field, unlike `expo-image-picker`'s gallery-asset object (which M2 already reads `asset.duration` from). Wall-clock timing across the record button's own start/stop taps is simpler and just as sufficient for this field's only real purpose — the existing resume-mismatch check's 2-second tolerance — as trying to read the resulting file's own encoded duration would be.

**Decision — a lightweight confirm step ("Captured X:XX — Retake / Start tagging"), not an automatic hard-cut into tagging.** The plan's literal "record a roll → tag immediately" wording was weighed against the real risk of a mis-tap (stopping a recording seconds after starting) dumping the user straight into a tagging session for a useless clip with no way back short of manually deleting tags. One extra tap on the success path preserves "tag immediately" in spirit while adding a cheap escape hatch — this project's own established preference for small deliberate UX judgment calls over literal-plan-compliance-at-any-cost (e.g. Stage S2's narrower deletion scope, M2's placeholder-over-hollow-shell choice).

**Gate outcome — code-reviewer found 2 HIGH, 2 MEDIUM, 1 LOW, all fixed in the same round.**

- **HIGH:** the permission-auto-request `useEffect` was keyed on `cameraPermission?.status`/`micPermission?.status` — but `requestCameraPermission()`'s own resolution changes `.status` (undetermined → denied), so the effect re-triggered itself. Since Android's `canAskAgain` typically stays `true` after a first denial, declining the very first native camera prompt fired a second, fully automatic native prompt with zero user interaction in between, then the same for microphone — up to 4 back-to-back system dialogs before the "access needed" fallback screen ever rendered. Fixed by requesting exactly once, gated by a ref flag the moment both permission objects load from `null`, with the screen's own "Grant access" button as the sole retry path afterward.
- **HIGH:** the on-screen Close button is disabled while recording (clear evidence of intent — don't let someone leave mid-recording without stopping first), but that only guarded the rendered `Pressable`. Android's hardware/gesture back button bypassed it entirely (confirmed via grep: no `BackHandler`, no navigation listener, and `predictiveBackGestureEnabled: false` in `app.json` makes the pop instant, not even animated), abandoning the in-flight `recordAsync()` promise with the camera/mic session left in an unknown native state. Fixed with a `navigation.addListener("beforeRemove", ...)` handler (via `useNavigation()` from `expo-router` — the documented, stable public API for exactly this, not an internal React Navigation hook) that intercepts any removal attempt while recording and calls `stopRecording()` instead of letting the screen pop, plus a last-resort unmount-cleanup call to `stopRecording()` for whatever removal path even `beforeRemove` doesn't cover (e.g. an OS-level activity teardown).
- **MEDIUM:** the hand-off from this screen into `tag.tsx` (`router.replace`) raced two independent orientation locks — this screen's own unmount cleanup restoring portrait at the same moment `tag.tsx`'s mount effect locks landscape, with no guaranteed ordering between the two async `lockAsync` calls. The first place in the codebase where the _previous_ screen also held an orientation lock (the gallery-pick path from `index.tsx` never locked orientation, so nothing raced against it before). Fixed with a ref flag set immediately before the `router.replace` call, skipping this screen's own portrait-restore specifically for that one transition.
- **MEDIUM:** a permanently-denied permission (`canAskAgain: false` — a second Android denial, or "don't ask again") made `request*()` resolve immediately with no native dialog at all, so the fallback screen's "Grant access" button visibly did nothing. Fixed by detecting that case and swapping the button for `Linking.openSettings()` with updated copy explaining Settings is now the only path forward.
- **LOW:** the post-recording confirm screen only offered "Retake" (re-arms the camera for another take) or "Start tagging" — no way to simply leave without recording again first. Added a distinct "Discard" action.

**Reasoning.** Both HIGH findings are the same shape as findings this project's own gates have caught before (an exit path that has cleanup for one route out but not another — M3's `undoTimer` unmount gap, generalized here to a whole native camera/recording session rather than a JS timer) — worth taking exactly as seriously given the larger blast radius (a stuck native camera/mic session vs. a harmless stale `setTimeout`). The permission double-prompt is a genuine, everyday-reachable UX bug (anyone who denies the first camera prompt hits it) and borderline platform-guideline territory (auto-re-prompting without a fresh user-initiated action), not a nit.

**Verification.** Same honestly-scoped approach as every prior mobile stage: no native simulator/device, `expo start --web` plus compiled-bundle content checks (`Record a roll`, `Discard`, `Open Settings`, `beforeRemove`, `Captured`, etc. all confirmed present, both before and after the gate-fix round). `tsc --noEmit` clean across `apps/mobile` throughout — the typed-routes regeneration gotcha (new route files need one dev-server run before `tsc` recognizes them in `router.push`/`Href` string literals) recurred again here, same as M2/M3, and was resolved the same way.

**Alternatives considered.**

- _Use `expo-image-picker`'s `launchCameraAsync` instead of `expo-camera`'s own `CameraView`:_ rejected — hands off to the OS's native camera app, a context switch away from MatOS entirely, which doesn't match "record a roll → tag immediately"; `expo-camera` keeps the whole flow in-app.
- _Try to read the recorded file's actual encoded duration (e.g. via a quick `expo-video` load) instead of client-side wall-clock timing:_ rejected — meaningfully more code for a field whose only consumer is a soft 2-second-tolerance mismatch check; wall-clock timing is simpler and already sufficient for that purpose.
- _Ship the plan's literal "tag immediately" with no confirm step:_ rejected — a mis-tap trap (see Decision above) that a single extra tap on the success path avoids almost for free.
- _Manually wire `navigation.addListener('beforeRemove', ...)`'s internals from scratch, or reach for expo-router's internal (unexported) `usePreventRemove` hook:_ the latter rejected outright — not part of expo-router's public API surface, an internal implementation detail of its own navigator core; `useNavigation()` + the standard `beforeRemove` event is the documented, stable, public equivalent and was used instead.

### 2026-08-05 — Stage M6: push sends wired (mobile), all-reviewer gate, and a real pre-existing RLS gap found

**Context.** M6 (build sequence: "Push sends wired (promotion, class reminder, breakdown shared) via Supabase → Expo push"). Before building, confirmed scope with the user: class reminders need real infrastructure that doesn't exist yet — `classes` stores only `day_of_week`/`start_time` with no gym timezone concept anywhere in the schema, and a periodic "is a class starting soon" check needs an actual cron job (Vercel's Hobby tier only runs cron once/day, not enough for a pre-class reminder, unless the account is Pro). Belt-promotion and breakdown-shared pushes have no such gap — both are simple on-write-event triggers. User chose to defer class reminders and ship the other two now. The plan's own row marks this stage code-reviewer-only, but it turned out to need a real schema/RLS change (see below), so — matching this project's established precedent (Stage M1's bearer-token deviation, Stage M3's schema fix, etc.) — this ran as a full security+database+code gate instead.

**Decision — sends are plain server-side `fetch` calls to Expo's push API from the existing API routes, not a new Supabase Edge Function.** No Edge Functions infrastructure exists anywhere in this repo yet, and both trigger points (belt promotion, breakdown creation) already run inside `withAuth`-wrapped Next.js routes with a real authenticated context. `apps/web/src/lib/push/send-push.ts`'s `sendPushToMember(memberId, notification)` reads the target's `push_tokens` via the normal RLS-respecting client (not service-role — see the next decision), POSTs to `https://exp.host/--/api/v2/push/send`, and prunes any token Expo reports as `DeviceNotRegistered`. Wrapped in try/catch, never throws — matches `writeAuditLog`'s own established best-effort call-site convention; a push failure must never fail the write it rides along with.

**Decision — staff SELECT/DELETE RLS policies on `push_tokens`, not a fourth service-role carve-out.** Sending a push to _another_ member requires reading their token rows, which Stage M1's self-scoped-only `push_tokens_all_self` policy never allowed (correctly — nothing sent anything until this stage). CLAUDE.md Rule 4 scopes service-role usage to exactly three purposes (invite generation, audit log inserts, seeding); rather than expanding that list, a new migration (`20260805190000_push_tokens_staff_send.sql`) adds `push_tokens_select_staff`/`push_tokens_delete_staff`, gym- and role-scoped exactly like every other staff-visibility policy already in this schema (`memberships_select_staff`, `external_people_all_staff`). Additive alongside the existing self-scoped policy — RLS policies for the same command are OR'd together, so self-registration/unregistration is completely unchanged. Live-verified (not just read for plausibility): seeded a real disposable token for a test member, confirmed a real coach session's SELECT actually returned it (not silently empty), confirmed a real round-trip to Expo's actual push API for an intentionally-malformed test token returned a genuine `DeviceNotRegistered` ticket, and confirmed the DELETE policy let the coach's session prune it. Cleaned up afterward.

**Gate outcome — one HIGH (fixed, with real live-confirmed blast radius beyond this stage), one MEDIUM and one LOW accepted-and-documented, one LOW fixed.**

- **HIGH (security-reviewer, live-confirmed against `pg_policies` before any fix was written):** the breakdown-shared push always pointed at a breakdown the recipient's own RLS forbade them from ever opening. `breakdowns_all_own` requires `author_id = auth.uid()` across _every_ one of its branches (including the `member_id`-focus branch), and `breakdowns_select_staff` is staff-only — so a non-author member who is merely a breakdown's _focus_ has never had SELECT access to it, at any visibility, since Stage A1. This isn't a regression introduced by M6 — it's a pre-existing gap M6 was simply the first feature to actively surface to a real user via a notification promising something the database had always refused. Verifying it also surfaced a much larger, previously-silent implication: an athlete's own computed profile (`fetchAthleteProfileData`, Stage A5/A7, rendered by both web's `analysis/athlete/[id]/page.tsx` and mobile's Stage M5 `athlete/[id].tsx` when viewing _themselves_) has been silently excluding every breakdown a coach ever authored about them, even ones explicitly marked shareable with the gym — "my own profile" was only ever built from self-authored breakdowns, for every gym since Stage A5 shipped. Fixed with a second migration (`20260805200000_breakdowns_focus_member_visibility.sql`) adding a focus-member SELECT policy to `breakdowns` and both child tables (`breakdown_positions`, `breakdown_events`), gated on `visibility = 'gym'` — a `private` breakdown stays exactly what its name implies, invisible to its subject, by design; this only grants access to the case no existing policy ever covered (authored by someone else, about me, marked shareable). Also tightened the push-send condition itself to additionally require `created.visibility === "gym"` (a private breakdown-about-someone-else still correctly can't be seen by its subject even after the RLS fix, so the push must not promise it can be). **Live-verified with real consequence, not just a synthetic test:** created a disposable gym-visible and a disposable private test breakdown authored by the coach about a real seeded demo athlete, confirmed via the athlete's own real authenticated session that the gym-visible one now resolves and the private one still correctly returns empty — and in the course of that same test, discovered the athlete's own breakdown list _also_ now correctly includes a genuine pre-existing seeded breakdown ("dsad", authored by a third party) that had been silently invisible to her the entire time this schema has existed. Both disposable test breakdowns deleted afterward; the pre-existing one was left as real, now-correctly-visible data.
- **MEDIUM (security-reviewer, accepted and documented, not fixed):** `push_tokens_select_staff` lets any coach/owner read raw `expo_push_token` values directly via their own client session (browser devtools, a raw REST call), not just through the intended server-side `sendPushToMember` path. Unlike other staff-visible fields in this schema (names, belts, attendance — ordinary business data), a raw Expo push token is closer to a bearer credential: anyone holding it can call Expo's public push endpoint directly, with arbitrary content, indefinitely, fully bypassing this app's own trigger logic and audit trail. A structurally cleaner fix (mediating every send through a SECURITY DEFINER function that never returns raw tokens to any client, calling Expo from inside Postgres via `pg_net`) would need a new extension enabled and a meaningfully larger, still-async-HTTP-from-SQL-shaped lift than is proportionate for wiring up two notification types in an alpha demo app. Accepted as a deliberate tradeoff, same reasoning style as the 2026-07-20 CSP entry: coaches are already a trusted role tier (Rule 3), the blast radius is staff-only and gym-scoped (never cross-gym, confirmed by both reviewers), and the realistic worst case — a coach with devtools access crafting a spoofed push to one of their own gym's members — is a real but bounded risk for a single-demo-gym alpha, not one that justifies the added infrastructure complexity right now.
- **LOW (security-reviewer, accepted and documented, not fixed):** `push_tokens_delete_staff` has no constraint limiting deletion to tokens actually confirmed stale by Expo — a coach could delete any in-gym member's token row outright, silently unregistering their device, with no audit-log entry (this table's writes were never audit-logged, including its own self-scoped register/unregister path since Stage M1 — deliberate, matching the table's own "disposable, device-local, re-derivable data, not a business record" framing). Availability/annoyance impact only (a member stops receiving pushes until they reopen the app and re-register), no confidentiality or integrity consequence. Accepted as consistent with this table's already-established design posture rather than singling out one write path for an audit-log treatment the rest of the table has never had.
- **LOW (code-reviewer, fixed):** the mobile tap-handler's `isPushData` type guard validated only the `type` discriminant, not the companion id field (`memberId`/`breakdownId`) — a payload matching `{type: "breakdown_shared"}` with no `breakdownId` would have passed the guard and produced a silent `/analysis/undefined` dead link. Not reachable from either of this stage's two real senders (both always include the field), but cheap to close for a future third sender. Fixed by validating the companion field's presence and type per variant.

**Reasoning.** The HIGH finding is exactly the kind of thing an all-reviewer gate exists to catch, and fixing it in this same round (rather than shipping the push feature broken-by-design and separately ticketing the RLS gap) matches this project's unbroken practice — S1, S2, M3 all fixed foundational RLS gaps discovered mid-gate in the same round rather than deferring them. What makes this one notable rather than routine is that live-verifying the fix surfaced a real, previously-silent correctness bug in _already-shipped_ functionality (self-viewed profiles, live since Stage A5) — a good example of why this project's "live-verify, never just re-read as fixed" discipline matters: a synthetic-only test would have confirmed the push's own dead link was fixed without ever revealing that the same gap had been quietly wrong for every athlete's own profile view this whole time. The MEDIUM and LOW acceptances were both explicitly framed by the reviewer as "worth a deliberate decision" rather than "must fix" — documenting the reasoning here, rather than silently accepting or reflexively fixing, is the same discipline the CSP/Node-version entries already established for this kind of judgment call.

**Verification.** Same honestly-scoped approach as every prior mobile stage for the client-side pieces: no native simulator/device, `expo start --web` plus compiled-bundle content checks. No real EAS project is linked yet (Stage M0's known gap), so `getExpoPushTokenAsync()` can't succeed in this environment — full end-to-end delivery (server sends → a real device receives → user taps → app navigates) can't be verified live here, an honest gap consistent with every prior stage's "no native simulator available" limitation. What _was_ live-verified, repeatedly, against the real remote database and the real Expo push API: both trigger routes running cleanly end-to-end with a real coach session; the staff RLS read/delete policies actually functioning (not silently empty); a genuine `DeviceNotRegistered` round trip through Expo's real API with correct stale-token pruning; and, for the HIGH fix, a real authenticated athlete session confirming the exact before/after visibility change on both synthetic and genuine pre-existing seeded data. `tsc --noEmit` clean across all three workspaces throughout; `apps/web`'s production build re-confirmed clean after the gate-fix round.

**Alternatives considered.**

- _Build class reminders anyway this stage, picking a default gym timezone and accepting the Vercel cron-frequency limitation as a known gap:_ rejected per the user's own explicit choice — ship the two triggers with no infrastructure gaps now, revisit class reminders once the timezone/cron questions have real answers.
- _Read `push_tokens` via a service-role client instead of adding staff RLS policies:_ rejected — would mean expanding CLAUDE.md Rule 4's explicit three-purpose service-role scope for a fourth reason, when a gym/role-scoped RLS policy (the pattern already used for every other staff-visibility need in this schema) achieves the same result while keeping RLS the actual boundary, not an app-layer bypass.
- _Mediate push sends through a SECURITY DEFINER Postgres function to close the MEDIUM finding now:_ rejected for this stage — would need `pg_net` (a new extension) and async HTTP-from-SQL handling, a meaningfully larger lift than proportionate for two notification types in an alpha app; logged as a deliberate, reasoned accept instead of either silently shipping the gap unexamined or over-building a fix disproportionate to actual risk at this phase.
- _Defer the breakdown-visibility RLS fix to a future stage, since it predates M6 and isn't strictly this stage's own regression:_ rejected outright — it's the exact reason the push feature doesn't work for its entire real-world trigger population, discovered by this stage's own gate, with a well-scoped fix available; matches this project's consistent "the gate exists to catch this, fix it in the same round" practice, not a reason to carry a known-broken feature forward.
